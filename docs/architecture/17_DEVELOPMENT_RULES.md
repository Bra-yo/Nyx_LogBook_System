# 17. Development Rules

---

# Purpose

This document defines the mandatory development standards for the BGHub platform.

It serves as the single source of truth for all future development, whether performed by human developers or AI coding assistants.

Every feature, API, database change, UI improvement, and refactor must comply with these rules.

Failure to follow these rules leads to architectural inconsistency, duplicated functionality, technical debt, and unpredictable behavior.

---

# Core Principle

**Architecture always comes before implementation.**

Developers and AI assistants must understand the existing architecture before writing code.

Never build first and attempt to fit the architecture afterward.

---

# Before Writing Code

Every implementation must begin by answering:

- What problem is being solved?
- Which existing module owns this responsibility?
- Does this functionality already exist?
- Can an existing component be reused?
- Does this align with the architecture documents?

If the answer is unclear, implementation must stop until clarified.

---

Before implementing any feature, AI assistants and developers must review the relevant architecture documents.

Minimum reading order:

---

# Never Invent New Architecture

Do NOT create:

New modules

New workflows

New user roles

New dashboards

New relationships

New entities

unless explicitly requested.

Always reuse the existing architecture.

---

# Reuse Before Creating

Before adding anything new, search for existing:

Components

Hooks

Utilities

Services

API routes

Database models

Enums

Types

Dialogs

Forms

Tables

Cards

Avoid duplicate implementations.

---

# Respect Ownership

Each module owns specific responsibilities.

Examples

Learning Engine

↓

Learning Areas

Learning Paths

Competencies

Mentorship Engine

↓

Mentor Allocation

Mentor Capacity

Mentor Expertise

Assessment Engine

↓

Competency Assessments

Portfolio Engine

↓

Portfolio Generation

Do not move responsibilities between modules.

---

# Never Duplicate Data

Do not store the same information twice.

Always reference existing entities using relationships.

Bad

Store Learning Area name in multiple tables.

Good

Reference learningAreaId.

---

# Never Duplicate UI

Avoid creating:

Two pages for the same purpose.

Two forms for the same entity.

Two dashboards showing identical information.

Enhance existing pages whenever possible.

---

# Admin Owns Configuration

Administrators are responsible for configuring the system.

Examples

Learning Areas

Competencies

Competency Groups

Mentor Expertise

Mentor Capacity

Learning Path Templates

Notification Templates

Learners must never configure academic structures.

---

# Learner Restrictions

Learners cannot:

Choose Learning Areas

Choose Mentors

Assign Competencies

Generate Learning Paths

Approve Assessments

Modify Assessment Results

Generate Certificates

All of these are system- or administrator-controlled.

---

# Mentor Restrictions

Mentors cannot:

Create Learning Areas

Edit Competencies

Modify Learning Paths

Approve Payments

Manage Users

Change System Settings

Their responsibility is mentoring and assessment only.

---

# Build Small, Reuse Large

When implementing new functionality:

Prefer extending existing modules over creating new ones.

Small reusable additions are preferred over large isolated implementations.

---

# UI Rules

Always follow:

16_UI_DESIGN_SYSTEM.md

Requirements:

Enterprise appearance.

Consistent spacing.

Reusable components.

Responsive layouts.

Accessible interactions.

Avoid placeholder interfaces.

---

# API Rules

Every API must comply with:

14_API_STANDARDS.md

Including:

Validation

Authorization

Ownership checks

Consistent responses

Error handling

Transactions where required

---

# Database Rules

Every schema change must comply with:

15_DATABASE_CONVENTIONS.md

Never:

Rename existing models unnecessarily.

Break relationships.

Duplicate entities.

Destroy historical records.

---

# Business Rules

Business rules always take precedence over convenience.

Examples

Learning Areas replace Departments.

Learning Paths are generated by administrators.

Mentors are allocated by administrators.

Competencies belong to Learning Areas.

Projects support competency acquisition.

Portfolio is automatically generated.

Never violate these rules.

---

# AI Assistant Rules

AI assistants must:

Read architecture before coding.

Search existing implementation.

Extend before replacing.

Avoid assumptions.

Avoid placeholders.

Avoid mock implementations.

Never invent business rules.

Never remove existing functionality unless requested.

Always preserve backward compatibility.

---

# Code Quality

Every implementation must:

Compile successfully.

Pass linting.

Pass type checking.

Avoid duplication.

Use meaningful names.

Be documented where necessary.

---

# Testing Requirements

Every feature should be validated through:

Unit Tests

Integration Tests

Manual Testing

Regression Testing

User Acceptance Testing

Follow:

19_TESTING_AND_ACCEPTANCE.md

---

# Pull Request Checklist

Before merging:

✓ Builds successfully

✓ TypeScript passes

✓ Lint passes

✓ Architecture followed

✓ APIs documented

✓ No duplicated functionality

✓ Permissions verified

✓ Business rules respected

✓ Existing workflows unaffected

✓ Documentation updated

---

# Documentation Rule

Every architectural change must also update the relevant document inside:

docs/architecture/

Documentation is part of the implementation.

Code without documentation is considered incomplete.

---

# Future AI Context

When using AI coding assistants:

Always provide:

Relevant architecture documents.

Relevant schema.

Relevant APIs.

Relevant existing components.

Never ask AI to "build from scratch" unless creating an entirely new module.

The AI should behave as a contributor to the architecture, not as the architect.

---

# Definition of Done

A feature is only complete when:

✓ Business requirements are met.

✓ Architecture is respected.

✓ UI follows the design system.

✓ APIs follow standards.

✓ Database conventions are maintained.

✓ Permissions are enforced.

✓ Tests pass.

✓ Documentation is updated.

---

# Golden Rule

> **BGHub is a competency-based internship management platform. Every implementation must strengthen the existing architecture rather than bypass it. Consistency, maintainability, and correctness always take priority over speed.**
